### Key Findings

1. **Tiered replication saves 70-79% bandwidth** consistently across all entity counts. The savings actually improve slightly at higher counts because more entities are far apart (cold tier).

2. **The ceiling is NOT hardware-bound** -- CPU is 19-24%, memory is 23MB. The bottleneck is the simulation phase inside the 50ms tick budget. At ~5000 auth entities per server, simulation alone takes 12-15ms p50.

3. **No UDP drops or shadow staleness issues** at any scale. The 10-second cold tier (every 4 ticks per entity) keeps shadows fresh. Logs show only "ACK stale" INFO messages from load test connections that don't send ACK frames (expected).

4. **Metrics HTTP endpoint becomes unresponsive above ~5000 auth entities per server** -- not because it crashed, but because the tick loop starves the async runtime. This is a known issue (the metrics server shares the tokio runtime with the tick loop).

5. **Projected 80% ceiling: ~7000 auth entities per server (~21,000 total across 3 servers).** Extrapolating the linear budget growth (35-49% at 5000 auth/server), the 80% budget wall would be hit at approximately 7000 auth entities per server.

6. **Shadow count fluctuations** are normal -- NPCs with random walk AI spread across a 8000x8000 world move in and out of each other's AoI radius (500 units), so shadow counts vary tick-to-tick.

7. **Hot tier (20Hz, nearby)** stays proportionally small (3-6% of entities) because entities are spread across +-4000 units -- most are far from each other. The cold tier dominates.

## Issues Encountered
- Metrics HTTP endpoint timeouts at high entity counts (>5000/server). The sim-server's tokio runtime is shared between tick loop and metrics server. When tick times approach 50ms, the metrics endpoint cannot respond promptly. Not a crash -- just starved.
- Load test connections trigger "ACK stale" INFO logs because they receive but never acknowledge frames. Harmless but noisy.
