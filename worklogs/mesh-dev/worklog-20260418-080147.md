through WI-206 from `docs/mesh-architect/work-items/020-player-migration.md`.

## Issues Encountered / Design Notes

### 1. PROTOCOL_VERSION not bumped
The work-item instruction said "Going from 2 → 3". I verified in the
codebase that `PROTOCOL_VERSION` is used only in:
- `receiver.rs:204` (UDP peer wire-version check)
- `coordinator/main.rs:199` (Register message wire-version check)
- `coordinator_client.rs:45`, `network.rs:163` (serialize on Register +
  PlayerAssigned).

Since WI-200 doesn't change the UDP peer wire (Batch 4 is purely
client-server protocol) and ClaimPlayer is a serde-compatible
enum extension, bumping the shared constant would cause a false
version-mismatch on the UDP peer path. I left it at 2 and commented
this decision inline. Flagged in the worklog per the "do not deviate
without flagging" instruction.

### 2. ClientFrame Deref shim for tests
WI-201's enum change caused 112 test compile errors (frame indexing).
Rather than mechanically patching every site, I added a `#[cfg(test)]
impl Deref<Target=[u8]>` that panics on Text. This keeps the
production enum semantics strict (no implicit conversions) while
allowing tests to `frame[...]` as before. Minimal disruption.

### 3. Rebalance convergence makes player migration slow to trigger
On board verification, the first test with 6 clients on S1 did not
trigger player migration in 20s because NPCs sort first and drain at
~1-2 per 5s rebalance interval. With 15 clients on S1 (weighted 45 vs
~15 on others), the imbalance is large enough that after NPCs drain
(~60s) players start migrating. The unit test
`process_transfers_falls_back_to_player_when_no_npcs` proves the code
works with the right conditions; board verification confirms it
end-to-end but requires patience (~60s).

Not a bug — this is the designed sort preference (NPCs cheaper to
migrate). Future iterations could weight-bias the candidate selection
more aggressively when players dominate the load difference, but
that's out of scope for this batch.

### 4. Test harness state persistence
Consecutive verify-wi206.ts runs against the same boards produced
inconsistent results because NPC/Player distribution drifted. The
final run was done against a fresh-restart cluster.
