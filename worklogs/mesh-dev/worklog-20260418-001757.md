## Changes Made

### WI-135 (Shadow last_seen_tick reset on peer restart)
- `crates/sim-server/src/systems/inbound.rs`:
  - Added a reset-drain block at the TOP of `drain_inbound_events`, BEFORE the `peer_updates` loop. Takes `peer_session_resets` via `std::mem::take`, then for each reset:
    1. Queries all `(Entity, &AuthorityServer, &Shadow)` tuples.
    2. Collects the `Entity` handles whose `AuthorityServer == reset.server_id`.
    3. Two-phase walk (collect-then-mutate) to avoid a query-iter vs `world.get_mut::<Shadow>` borrow conflict.
    4. Sets each affected `Shadow.last_seen_tick = 0`.
    5. Logs at `info` with `server_id`, `new_session_id` (hex-formatted), and `shadows_reset` count.
  - Ordering (reset -> peer_updates) is load-bearing: without it, a same-tick low-tick post-restart update would still be rejected by the `update.tick < shadow.last_seen_tick` guard.
- `crates/sim-server/src/resources.rs`:
  - Removed `#[allow(dead_code)]` on `PeerSessionReset` (now has a production consumer).
  - Updated doc comment to point at the implemented consumer instead of the forthcoming one.

## Issues Encountered
- `drain_inbound_events` uses `&mut World` (not a system closure), so the standard ECS pattern of `world.query::<...>` inside the fn + the borrow checker required a two-phase walk: first `query.iter(&*world)` collects entity handles, then a separate loop does `world.get_mut::<Shadow>(entity)` mutations. This is idiomatic for `&mut World` systems in Bevy and matches the existing patterns already used in `drain_inbound_events` (the peer_updates loop uses the same dance).
- The `session_id()` getter on `MetricsCollector` triggered a `dead_code` warning since no production call site reads it back (the setter is the only write; all reads go through `snapshot()`). Resolved with `#[allow(dead_code)]` + a doc comment noting the getter exists for tests and future dashboard/debug consumers. Preferred this over `#[cfg(test)]` because keeping a normal public method for operator tooling is simpler than conditionalizing it.
- First-sight session recording in `note_session` now takes the `peer_health` lock unconditionally. This is an extra mutex acquisition per first-sight packet, but first-sight is O(peers) over the server's lifetime — not a hot path. The trade is: simpler metrics semantics (peer_sessions always reflects current session) vs. one extra lock per peer once ever.
- One nit: the existing `snapshot_deserializes_back` test asserts exact key presence on `peer_health[2]` but doesn't explicitly assert `session_id`. I chose to leave it alone rather than alter its assertion set — the new test `snapshot_includes_local_and_per_peer_session_id_in_json` covers that explicitly, and the existing test remains a valid round-trip check for the pre-existing fields. The comprehensive `snapshot_all_new_fields_present_in_json` test IS updated to require `session_id` in its `required_fields` list.
