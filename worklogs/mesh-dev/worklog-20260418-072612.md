## Issues Encountered

### No systemd service file on the boards
The WI-193 spec says "check `/etc/systemd/system/mesh-sim-server.service`
for `KillSignal`" but there is no such file on the boards. The
sim-server is started via:
- `./start-unoq.sh` using `nohup bash -c '... sim-server ... &'`
- Board dashboard `/api/mesh/start` (spawns via `Command::new(&cfg.binary).spawn()`)

Stopped via `pkill -f sim-server` in stop-unoq.sh AND in board-dash
`/api/mesh/stop` — both send SIGTERM by default. Our code now catches
both SIGINT (tokio signal::ctrl_c) and SIGTERM (signal::unix with
SignalKind::terminate()) so all current shutdown paths hit the
graceful drain.

### Recovery-race double-counting (finding 084, Batch 5 territory)
After drain completes, the sim-server exits -> TCP disconnects from
coordinator -> coordinator treats disconnect as a crash -> broadcasts
RECOVERY -> survivors promote shadows to authoritative, duplicating
what drain already transferred. This is a known problem (audit 084,
part of Batch 5 per design 016). Not in scope for Batch 3.

Observable symptom: Scenario 1's final count was S2=29 + S3=29 = 58
vs. expected 46. The +12 is shadow-promotion duplication.

### Scenario 2 partial spawning
My WSS spawn driver sent 100 SpawnEntity messages but only 6 landed
on S2. Could be WS sender backpressure / tokio channel bounded-drop.
Not relevant to Batch 3's drain behavior — drain handled all 33
entities that were on S2 at SIGTERM time. Could be diagnosed with
board metrics but not in scope.
