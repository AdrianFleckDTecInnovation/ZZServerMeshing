## Changes Made

### WI-137 — `tools/test-suite/scenarios/peer-restart-reconvergence.ts`
New scenario. Spawns 500 entities, kills S2, restarts, spawns 200 more, polls metrics for:
- (A) survivors' `peer_health[2].session_id` equals S2's new local `session_id`
- (B) `peer_health[2].chunk_evictions` stable across two samples (no accumulation)
- (C) `peer_health[2].latest_tick` within 20 ticks of S2's current tick

Board mode detected via `METRICS_HOSTS` env. In board mode kill is SSH `pkill -9 -f sim-server`, restart is SSH `nohup ~/mesh/sim-server ...` (same shape as `start-unoq.sh` uses). Local mode uses `lsof` + `cargo run` spawn.

MAX_POLL_MS is 60s to absorb the initial cargo/cross-compile restart cost and the 5 s coordinator rebalance interval (a brand-new S2 has no entities until rebalance feeds it).

### WI-138 — `tools/test-suite/scenarios/peer-restart-twice.ts`
Same template, two back-to-back restarts. Asserts all three session_ids (A, B, C) differ, then polls same (A)/(B)/(C) on session C.

### `tools/test-suite/runner.ts`
- Imported + registered both new scenarios.
- **Precision-safe u64 parsing** (critical): the Rust `/metrics` endpoint emits `session_id` as a JSON number (u64 decimal). JavaScript `Number` silently drops low bits for values above 2^53, which would cause false negatives in these tests. Added a regex pre-pass on the raw text before `JSON.parse` to extract all `session_id` values as decimal strings, then rewrite the parsed object so scenarios see strings.
- Fixed a subtle regex bug in the peer_health extractor: the original bounded-brace pattern `\{[^}]*(?:\{[^}]*\}[^}]*)*\}` terminated at the first inner closing brace and captured only the first peer entry (verified live against `localhost:8101/metrics` with 2 peers — only peer 3 was being read). Replaced with a simpler approach: locate the `"peer_health"` key, then apply a global regex `"(\d+)"\s*:\s*\{[\s\S]*?"session_id"\s*:\s*(\d+)` to the tail.

### `tools/test-suite/types.ts`
Added `PeerHealthSnapshot` interface with `session_id: string` (decimal, precision-preserved). Extended `ServerMetrics` with optional `session_id?: string` and `peer_health?: Record<string, PeerHealthSnapshot>`. JSDoc explains the precision rationale.

### `test-scene.sh`
Appended `peer-restart-reconvergence,peer-restart-twice` to the scenario list so `./test-scene.sh` includes them.

## Issues Encountered

1. **Stale binaries skipped rebuild** — `start-unoq.sh` checks `[ ! -f target/.../sim-server ]` before invoking `cargo zigbuild`. With binaries from prior sessions the rebuild was skipped, so the first board deploy shipped pre-Batch-1 code (metrics had no `session_id` field). Fix: deleted the binaries and re-ran. Consider a `--force` flag on the script for future work.

2. **JS u64 precision loss** — initial test run showed survivor session_id hex differing from S2's own by the low bits. Root cause: `JSON.parse` in `runner.ts` was casting `session_id` to JS `Number`. Fixed with regex pre-extraction (see runner.ts section). Verified live: session ids like `0x87f14501c2526cc3` (which exceed 2^53) now round-trip exactly.

3. **Peer_health regex bug** — the bounded-brace pattern only captured the first peer entry, causing survivor-sees-peer checks to silently read the wrong peer's session. Fixed by scanning from the `peer_health` key onward. Confirmed fix by live-scraping both peers.

4. **Dashboard zombie children** — pre-existing issue: board dashboard's `/api/mesh/start` uses `Command::spawn()` with stdio redirected to `/dev/null` and never awaits the child, so a killed sim-server becomes a permanent zombie and subsequent starts return `{"error":"already running"}`. First kill/restart cycle worked; the second broke board state until the dashboard systemd service was bounced. Fix: the scene tests in this batch bypass the dashboard entirely and use SSH `pkill` + `nohup sim-server &` to match what `start-unoq.sh` does at cluster bring-up. Documented in the `killBoard`/`restartBoard` source comments. A separate follow-up work item should fix the dashboard to reap children properly (not scope of Batch 4).

5. **MAX_POLL_MS was too short** — initial value of `CONVERGENCE_POLL_TICKS * TICK_MS * 3` (6 s single-restart) and `* 4` (8 s twice-restart) routinely hit the budget during cargo/coordinator rebalance waits. Raised both to 60 s with explanatory comments. Real reconvergence once UDP packets start flowing is well under 1 tick.

6. **multi-client fallback is wrong in board mode** — pre-existing bug unrelated to this batch. When `/servers` lookup fails it toggles port 7878↔7879 on the same host, which on boards gives invalid host:port pairs. Noting here for a future issue.
