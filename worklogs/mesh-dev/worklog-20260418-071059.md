## Changes Made

### WI-180 — `client/src/network.ts`
- Added `coordinatorUrl: string` field, populated in constructor. Removed
  the `url: string` constructor param; `this.url` is now populated
  asynchronously from `fetchAssignment()`.
- Added `private serverDirectedUrl: string | null = null` to track
  `Reconnect { url }` directives from the server. Consumed exactly once
  by `scheduleReconnect`.
- New `private async fetchAssignment(): Promise<string | null>` — makes
  the HTTP `/assign` call with the configured coordinator URL (falls back
  to same-origin `/assign` when `VITE_COORDINATOR_URL` is empty). Returns
  `null` on non-2xx, network errors, or missing `ws_url`. Logs warnings
  but never throws.
- New `private async init(): Promise<void>` — fetches the initial
  assignment, then calls `connect()`. If `/assign` fails on bootstrap,
  `this.url` stays empty and `connect()` falls through to
  `scheduleReconnect()` which retries on backoff. Logs
  `"Assigned to server: {url}"` on success to keep the existing
  regression-check log line.
- Constructor now calls `void this.init()` (fire-and-forget) instead of
  `this.connect()` directly.
- `connect()` now guards against empty `this.url` — if no URL, skip the
  `new WebSocket('')` (would throw SyntaxError) and schedule another
  reconnect to retry `/assign` on backoff.
- `Reconnect` handler now sets `this.serverDirectedUrl = msg.url` (plus
  the existing `this.url = msg.url`) so the next `scheduleReconnect`
  honours the server directive instead of overriding it with a fresh
  `/assign`. Comment documents why: Batch 4 player migration will steer
  clients to specific targets.
- `scheduleReconnect` is now async. If `serverDirectedUrl` is set,
  consume it (clear to null) and skip `/assign`. Otherwise await
  `fetchAssignment()`; if fresh URL differs from current, log
  `/assign returned new URL: {fresh} (was {old})`; if same, log
  `/assign returned same URL: {fresh}`; if null, log
  `/assign unavailable, retrying last-known URL {url}`. Always call
  `connect()` after.
- `getServerUrl(): string` public accessor unchanged — still returns
  `this.url`. The debug overlay at `main.ts:30` keeps working.

## Issues Encountered

### First run: `pgrep -f sim-server` race in startSim
The initial `startSim` helper used `pgrep -f sim-server && echo ALREADY_RUNNING ||
start` to avoid double-starts. This matched a freshly-killed but still-dying
process and skipped the start. Scenario A's "restart S3" left the cluster
at 2 servers, causing B and C's preconditions to fail.

**Fix:** Removed the `pgrep` guard. `startSim` now just does `setsid bash -c
'nohup sim-server ... </dev/null > log 2>&1 &'`. The `setsid` + explicit
stdin redirect fully detaches from the SSH session so the process doesn't
die when SSH exits. The sim-server is already tolerant of double-starts
(second one collides on the port and exits) so the guard wasn't needed.

### Initial recovery timing in Scenario C (first run)
Initial pass condition for C required `assignFresh > 0 && connects >= 2`
within 25s. Because coord returned the *same* URL (client was on S2, S2 is
still the least-loaded post-restart), no `assignFresh` log fired —
`assignSame` did. The assertion window timed out by 77ms despite the
client actually reconnecting successfully.

**Fix:** Changed the pass condition to `connects > connectsAtRecovery`
— i.e., "any new connect event after the stop". This is the correct
signal for recovery regardless of whether /assign returned a new URL
or the same one. On rerun, Scenario C passed with 1001ms recovery time.

### One open behavior note on Scenario A
The reconnect log sequence is:
```
[onclose]  Disconnected from server
[setTimeout 1s]
[scheduleReconnect]  Reconnecting in 1000ms...
[/assign returned new URL: ...]
[connect]  Connecting to wss://...
[connect]  Connected to server
```
This means post-kill recovery time = exponential-backoff delay +
`/assign` round-trip. On the first crash it is ~1500ms end-to-end; on
sustained crashes the backoff doubles up to 10s per the existing
`RECONNECT_MAX_DELAY_MS` cap. This matches the WI spec ("up to
`RECONNECT_MAX_DELAY_MS` per the config"). The WI said "entities render
again within 2–5 seconds" for Scenario A — we hit the low end (~1.5s)
because the first retry happens on the minimum backoff.

### The Reconnect-handler subtlety
The WI highlighted that the `Reconnect { url }` handler must not let a
subsequent `/assign` refetch override the server-directed URL. Implemented
via the `serverDirectedUrl: string | null` field that is set by the
handler and consumed-and-cleared by the next `scheduleReconnect` run.
Not exercised in WI-181 verification (Batch 4 will send `Reconnect`
messages; nothing does today), but the unit is shaped correctly.
