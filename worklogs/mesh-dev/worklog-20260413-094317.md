## Design Decisions
- **Baseline updated immediately after sending** (not waiting for ACK). The design doc considered tracking separate "sent" vs "confirmed" baselines but opted for the simpler approach since WebSocket is TCP-based (frames are reliable). The periodic full snapshot every 5 seconds handles any edge case.
- **ACK stored in AtomicU64** shared between async handle_client and ECS game loop. Currently the acked_tick is not used for conditional baseline confirmation, but the infrastructure is in place for future optimization (only updating baseline when ACK confirms receipt).
- **NEXT_CLIENT_ID is a static AtomicU64** rather than being part of ClientRegistry, because client IDs must be assigned in the async handle_client task before the registration event reaches the ECS. This avoids needing to pass a shared mutable registry across async boundaries.
- **ClientSnapshot resource retained** for backward compatibility. Schedule tests check `ClientSnapshot.frame` to verify binary format. The system writes a full snapshot to it every tick AND sends per-client frames through mpsc channels.
- **RequestSnapshot routes directly to force_full_snapshot_clients** instead of going through ClientMessage pipeline, because ClientMessage inputs have no client ID. The handle_client task intercepts RequestSnapshot before pushing to client_inputs.
