## Issues Encountered / Design Notes

### 1. WI-212 `latest_tick` handling deviation from spec
The WI-212 spec says "Remove the three `.remove(&server_id)` calls at
`receiver.rs:69-71`" which targets `latest_tick`, `packets_received`, and
`chunk_evictions`. I kept `packets_received` and `chunk_evictions`
preserved (per spec goal: continuous counters across restart), but still
reset `latest_tick` on session change.

Rationale: `latest_tick` is specifically the highest tick we've seen from
this peer's CURRENT SESSION. A restarted peer begins at tick 0, so the
old session's high-water mark is not meaningful for the new session. Left
intact, `staleness_ticks` (= our tick − latest_tick) would perpetually
report "1000 ticks behind" long after the restart, making the metric
mislead operators. `session_changed_at_tick` provides the continuity
signal for "when did restart happen" without the staleness confusion.

Updated both `PeerHealthAccumulator.latest_tick` doc and the
`session_change_does_not_zero_packets_received` test to reflect this.
Documented inline in note_session.

### 2. peer_health map also pruned on WI-213 sweep
The WI-213 spec itemizes pruning `session_of_peer`, `latest_tick`, and
`session_history`. These are the RECEIVER-LOCAL maps. But the
`peer_health: SharedPeerHealth` ALSO has per-peer maps
(`latest_tick`, `packets_received`, etc.) that are exposed on `/metrics`.
Without also pruning those, departed peers would still show up on
`/metrics` with stale staleness values for a long time.

Added peer_health-map pruning to the same sweep. Logged as
`peer_health_pruned=<N>` for observability.

### 3. Recovery adoption on rolling redeploy inflates auth count briefly
After a rolling redeploy of all 3 boards, total auth temporarily climbs
from 46 → 72 before rebalance settles. This is NOT a WI-215 regression
— each restart has `cold_start=false` and skips initial_npcs (verified
in log "ECS World initialized with 0 NPCs"). The inflation comes from
shadow promotion: when S3 crashes (or takes >15s to restart), S1 and S2
adopt its shadows via `RecoverEntities`. When S3 comes back, rebalance
sends some back. Pre-existing behavior, unrelated to this batch.

If WI-215 had failed, the count would grow by +20 per restart — so 46 +
60 = ~106. Observed 72, well below that ceiling.

### 4. session_changed_at_tick interacts with WI-213 prune
Observation: after a WI-213 prune removes a peer's entry entirely, a
subsequent re-register is treated by `note_session` as "first sight"
(None branch) → no `session_changed_at_tick` update fires for this
transition. Operators can still detect the restart via `session_id`
change relative to their own snapshots, or the `active_peers` change
visible in coordinator telemetry.

This is a deliberate side-effect of the WI-213 prune + WI-212 semantics
coexisting. Documented in the note_session doc. Not a bug — the
`session_changed_at_tick` field is specifically for "session change
without intervening prune" (the rolling-deploy case); the prune-then-
re-register case is already distinguishable via active_peers.

## Deviations
1. **WI-212 `latest_tick` reset** (detail above). Spec said remove all 3
   `.remove()` calls; I kept `latest_tick` reset because of the staleness
   interaction. Test updated to match.
2. **WI-213 adds peer_health pruning** not explicitly in the spec, but
   needed so `/metrics` reflects departed peers cleanly.
3. **board-dash `MESH_ARGS` does NOT pass `--cold-start`**. The work
   item said "check board-dash code for this; decide based on semantics."
   Semantic analysis: the Start Server button on the board dashboard
   launches a sim-server process — if the previous one died/was stopped,
   the survivors have already adopted its entities. Re-spawning
   `initial_npcs` would duplicate them. So Start = restart, not
   bootstrap. Omitted `--cold-start` from MESH_ARGS with an explanatory
   comment in start-unoq.sh.
