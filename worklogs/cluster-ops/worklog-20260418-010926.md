### In-flight transfer timeout mechanism
**None.** `record_transfer_result` (registry.rs:177–194) is the *only* path that decrements `in_flight_transfers`. It is only invoked when the coordinator receives a `TransferResult` CoordClientMsg from the source server. There is:
- No timeout / TTL on in-flight transfers
- No clearing on peer topology change
- No clearing on drain / recovery broadcast
- No clearing even when the *target* server dies (only the source's counter matters, but the source may never send TransferResult if it was in the middle of the handoff when its peer crashed)

If a `RebalanceDirective` is emitted and the source never produces a `TransferResult` for any reason — target crash mid-transfer, UDP drop of the AuthorityTransfer packet, source crash before it can report back, bug in drain path — the counter is stuck at ≥1 forever. Once stuck, `try_rebalance` at L240–243 filters that server out of the `overloaded` candidate set **permanently** via `.filter(|s| s.in_flight == 0)`.

### Root cause
Hypothesis 1 is the most likely explanation, with an important refinement:

1. Scene tests around 18:00:39–18:00:44 crashed S2 ("peer-restart" tests). S2 re-registered at 18:00:44 (see journal: `Registered S2 ... | 3 servers total`).
2. From 18:00:55 through 18:01:55, S3 was the most-loaded survivor and emitted 8 `RebalanceDirective`s toward S2. Each one incremented `S3.in_flight_transfers`. Entity counts in the logs (S3: 18→11, S2: 0→7) suggest **some** TransferResults did come back — 7 successful decrements reflected in S2 growing by 7, S3 shrinking by 7. So at minimum the 8th transfer (or one of them mid-stream) never produced a TransferResult, leaving `S3.in_flight_transfers >= 1`.
3. Post-18:01:55, S1 climbs to 28 (likely from scene-test spawn tail-off or normal client traffic) while S3 holds at 10 and S2 holds at 8. The new most-overloaded is S1.
4. `try_rebalance` does `.filter(|s| s.in_flight == 0).max_by_key(|s| s.weighted_load)` — this filter only applies to `overloaded`, not `underloaded`. So if `S1.in_flight == 0` it should be picked. But the empirical evidence is that no directive fires. Given that weighted_load = 3·players + 1·NPCs, and all spawned entities from scene tests are NPCs, S1=28, S3=10, S2=8 gives avg=15.33, diff=S1−S2=20, 20%·avg=3.07. Thresholds (`diff ≥ 10 && diff ≥ avg·0.2`) are clearly met.
5. That leaves two suspects:
   - **(a) S1's `in_flight_transfers` is also stuck >0** from an earlier rebalance we can't see in the tail (the `status` output only shows 10 lines; there may have been earlier S1→X directives before 18:00:55). If S1 is filtered out, the only remaining overloaded candidate is S3 (10) and underloaded is S2 (8), diff=2 < 10, so no directive — matches the observation.
   - **(b)** Weighted-load mismatch where sim-servers report weighted_load differently from entity_count. The `/servers` endpoint only surfaces `entity_count`; `weighted_load` is private to the registry. If heartbeats send `weighted_load=0` the fallback at L112 uses `entity_count`, which is fine. But if they send a non-zero weighted_load that happens to make S1≈S3≈S2 in weighted terms (e.g. S2/S3 have players, S1 has only NPCs: S2=8 NPCs→8, S3=10 NPCs→10, S1=28 NPCs→28), the thresholds still trip. So (b) is unlikely to be the sole cause.

Most probable root cause: **stuck `in_flight_transfers` counter** on one or more sim-servers (likely both S1 and S3 have accumulated undecremented counts from the scene-test churn; S2 crash-and-reconnect cycles lost the TransferResult reply path for in-flight outbound transfers from its peers). `record_transfer_result` has no timeout/reset, so the counter is monotonically stuck, and `try_rebalance`'s `in_flight == 0` filter silently excludes the real overloaded servers. This matches hypothesis 1 exactly.

Hypothesis 2 (task not running) is unlikely — the systemd process is up, CPU=7.773s over 21min indicates active work, and the rebalance cadence was regular right up until 18:01:55. Hypothesis 3 (heartbeat mismatch) is unlikely given `/servers` shows sane entity counts updating in real time.

### Proposed fix (design-level, not implemented)
Three complementary mitigations, from cheapest to strongest:

1. **TTL on in-flight transfers.** Add `transfer_started_at: Instant` to each in-flight entry (convert `in_flight_transfers: u32` into `Vec<TransferInFlight>` or similar). In `try_rebalance` (or a periodic sweep), prune entries older than e.g. 30s and log at `warn!`. This is the minimum fix and directly closes the leak.
2. **Clear in-flight on peer death / re-register.** In `unregister` and the disconnect path, when server X disappears, decrement in_flight counters on all *other* servers that had transfers targeting X (requires tracking target_server per in-flight entry — same data model change as #1). Also reset the source's own counter to 0 on its own re-registration.
3. **Elevate the rebalance-check log to INFO (or wire RUST_LOG=debug into the systemd unit).** The fact that we cannot distinguish "skipped — in_flight" from "skipped — thresholds" from the production logs is itself an operational defect. Either promote the per-iteration summary to INFO (once per 5s is fine) or include `in_flight` in the directive log and add a one-line `Rebalance skipped:` INFO log when thresholds trip but a filter excludes a candidate.

Immediate workaround (no code change): restart the coordinator — `systemctl --user restart mesh-coordinator`. Registry is in-memory; counters reset to 0; sim-servers auto-reconnect. Load-balancing will resume on the next 5s tick. This is safe because coordinator is stateless w.r.t. game state.
