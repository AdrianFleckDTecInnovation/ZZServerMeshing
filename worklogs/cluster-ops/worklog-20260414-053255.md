All 3 servers marked dead during steady-scale rebalancing, same pattern as previous run.

#### Sim-Server Side: Abort Not Detected

S1 log shows it received a rebalance directive at **05:36:29** -- which is **11 seconds AFTER** the coordinator marked it dead at 05:36:18 and called `abort.abort()`. After 05:36:29, no more coordinator messages arrived, but S1 NEVER logged "Lost coordinator connection" and NEVER re-registered.

The WebSocket abort fix has the right structure in the code:
- `registry.unregister()` at line 72-79 calls `abort.abort()` on the connection task
- `coordinator_client.rs` line 68 loops on `ws_stream.next().await` which should return `None` when aborted
- Line 125 logs "Lost coordinator connection" which was never seen

The abort kills the coordinator-side tokio task but does NOT reliably close the TCP connection in a way that the sim-server's WS reader detects. The sim-server's `ws_stream.next().await` appears to hang indefinitely rather than returning `None`.

#### Why the Abort Fails

The abort kills the coordinator's connection handler task, but:
1. The TCP connection may not be cleanly closed (no FIN/RST sent) -- aborting a task drops its future but may not flush/close the underlying TCP stream
2. TLS adds another layer -- the TLS session may buffer without a clean shutdown
3. The sim-server's WS reader blocks waiting for the next frame, which never arrives but the TCP keepalive hasn't fired yet

## Recommended Fix

The `abort.abort()` approach does not reliably close the TCP connection. Instead, the coordinator should:
1. Send a WebSocket Close frame before removing the server
2. OR explicitly close/drop the `reply_tx` sender, which would cause the sink task to exit and the WS to close
3. OR send a "YouAreDeregistered" message that the sim-server handles by disconnecting and reconnecting
