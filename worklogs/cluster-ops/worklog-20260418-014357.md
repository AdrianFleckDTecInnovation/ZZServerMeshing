## rebalance-stuck-recovery diagnosis

**Two-part failure, neither part implicates the WI-141/142/143 fix:**

### Part 1: TLS (infra-level, masks everything)
`tools/test-suite/scenarios/rebalance-stuck-recovery.ts:78` calls `fetch(${COORD_HTTP}/servers)` with no agent. Node's global fetch rejects the self-signed cert and the scenario short-circuits at `fail('Coordinator /servers unreachable')`. Every other scene scenario has the same vulnerability but none of them talk to the coordinator; most talk to sim-server WebSockets (WSS) which go through a different code path (`ws` library) that's already configured to ignore cert errors project-wide. The fix is either:
  - set `NODE_TLS_REJECT_UNAUTHORIZED=0` in `test-scene.sh`'s invocation, OR
  - build an `https.Agent({rejectUnauthorized: false})` in the scenario file and pass it to `fetch()` via `dispatcher` / `undici.Agent`.

Verified the WI-142 fields *are* read correctly once TLS is bypassed — the scenario advanced past its sanity check (`Pre-test: ttl_prunes_total=0`).

### Part 2: Directive-observation window (scenario-tuning, board-specific)
After `NODE_TLS_REJECT_UNAUTHORIZED=0`, the scenario spawned 300 NPCs on ctx.server (assigned to S2), then polled `/servers` every 50 ms for 30 s looking for `in_flight_transfers >= 1`. Observed 0 the entire time.

But the coordinator journal shows 9 rebalance directives fired during that window (18:53:16 through 18:54:16), transferring 2–3 entities each. Sample lines:
```
Apr 17 18:53:16 Rebalancing: S3 (36 entities) -> S1 (25 entities), transferring 3
Apr 17 18:53:21 Rebalancing: S3 (33 entities) -> S2 (0 entities), transferring 3
Apr 17 18:53:36 Rebalancing: S1 (28 entities) -> S2 (5 entities), transferring 2
```
Between each log line the source's `entity_count` drops by exactly the directive size (36→33, 33→29 via 2 transfers + own activity), which means **every TransferResult is arriving well before the next 5 s rebalance tick**. The in-flight window per directive is <200 ms on the LAN. A 50 ms `/servers` poll can miss it, especially because `/servers` traverses a `tokio::RwLock::read().await` and the coordinator's tokio runtime competes with the rebalance task for that lock.

Corollary: the healthy `in_flight_transfers=0` and `ttl_prunes_total=0` values at the end of the test are **proof the new coordinator is working correctly**, not evidence of a bug. No leak, no stuck slot. There is simply nothing for the TTL to prune because transfers are completing cleanly.

Scenario calibration would need:
  - lock the coordinator's rebalance task (e.g. inject a SIGSTOP on the source sim-server so TransferResult never sends) rather than trying to catch the race, OR
  - poll `/servers` at the same cadence the coordinator's rebalance task holds the write lock (sub-5ms), OR
  - add a testing hook to the coordinator that deliberately holds an in-flight slot open.

## Anomalies flagged (not fixed per task instruction)

1. **BUG (scene-test infrastructure):** `tools/test-suite/scenarios/rebalance-stuck-recovery.ts` uses plain `fetch()` against the coordinator, which breaks on self-signed TLS cert used in board deployments. Every other coordinator-touching scene test would have the same problem (none currently do). Fix: add TLS-bypass `https.Agent` wiring, or document that `NODE_TLS_REJECT_UNAUTHORIZED=0` is required for this scenario in BOARD_MODE.
2. **LIMITATION (scene-test design):** The "observe an in-flight directive via /servers polling" design cannot reliably fire on a 3-board LAN cluster because transfers complete faster than the minimum polling round-trip. The WI-143 scenario as written is effectively a localhost-only test. For real board verification, the scenario needs either a coordinator test hook or a deliberately-stuck sim-server (e.g. via SIGSTOP on the rebalance source between receiving RebalanceDirective and sending TransferResult).
3. **BUG (test-scene.sh):** `./test-scene.sh --no-start` always routes through `./test.sh` which hard-codes `curl localhost:7871/assign` for readiness — no env-var override for board deployments. Has to be bypassed by invoking `tools/test-suite/runner.ts` directly. Documented in `start-unoq.sh`'s trailing help text but easy to miss.
4. **BUG (scene test - multi-client):** picked client-2 server as `wss://192.168.0.86:7878` (S3's host with S1's port) — confused host and port when assigning a secondary server. Pre-existing, unrelated to this deploy.
5. **NOT-A-BUG (scene test - authority-transfer WARN):** only 2 transfers observed because the new coordinator rebalanced the spawn burst so aggressively during the 300 ms settle that by the time the scenario checked `imbalance_ratio` it had already dropped under its trigger threshold. Symptomatic of the fix working *too* well for this scenario's timing assumptions. No action needed.
