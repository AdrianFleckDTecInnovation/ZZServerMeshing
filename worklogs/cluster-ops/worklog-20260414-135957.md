### Critical Finding: UDP Replication Channel Saturation

At ~600-800 total entities, UDP replication starts dropping packets:

| Board | UDP Drop Warnings | Peak Drops/5s |
|-------|-------------------|---------------|
| unoq (S1) | 84 warnings | 4,509 drops/5s |
| unoq2 (S2) | 81 warnings | 6,443 drops/5s |
| unoq3 (S3) | 90 warnings | 2,194 drops/5s |

The drops started at ~14:02:03 UTC, approximately when the cluster hit 600-800 entities during steady-scale. By 1300+ entities per server, every server was continuously dropping thousands of replication packets per 5-second window.

**Impact:** Shadow counts become unreliable at scale:
- Post-test: S1 had 2666 shadows, S2 had 2714 shadows, but S3 had 0 shadows
- Peer count dropped from 2 to 1 on some servers during heavy load
- Replication data integrity degrades before tick budget becomes an issue

**This means: the true scaling limit on the boards is NOT tick budget (~9000 extrapolated) but UDP channel capacity (~600-800 entities before replication quality degrades).**

## Key Findings

1. **Tick budget is NOT the bottleneck.** At 3000 entities (1000/server), peak budget was only 27%. Extrapolating, the boards could handle ~9000-10000 entities on tick budget alone.

2. **UDP replication channel is the real bottleneck.** At ~600-800 entities, the replication channel starts dropping packets. At 1000+/server, drops reach thousands per 5 seconds. This breaks shadow replication before tick budget becomes an issue.

3. **AoI filtering helps client bandwidth but does NOT help UDP replication.** UDP replication sends ALL authoritative entities to ALL peers regardless of AoI. AoI only filters what goes to WebSocket clients.

4. **Shadow processing is expensive.** S3 with 0 shadows and 1337 auth entities used 6.6% budget. S1/S2 with similar auth counts but ~2700 shadows used 29-32% budget. Shadows cost roughly 4x the tick budget of auth entities.

5. **The spatial-hotspot test runner needs to handle partial metrics gracefully** (does not crash when some servers are missing from the coordinator registry).

## Recommendations

1. **Apply AoI to UDP replication** -- each server should only replicate entities that are within the AoI of entities on the receiving server, not broadcast everything. This is the highest-impact change.
2. **Increase UDP channel buffer size** -- currently saturates at ~600 entities, should be tuned for 3000+ entity workloads.
3. **Add `STEADY_SCALE_MAX` higher cap** (e.g., 10000) and re-run to find the true tick budget ceiling now that AoI is active for client broadcast.
4. **Fix spatial-hotspot crash** -- guard against undefined metrics when servers are missing from coordinator registry.
